### ⚠️ Environment facts that cost hours THIS session

Carry these forward — they are new, and each one cost a debugging detour.

- **`.next` goes stale and the login form stops hydrating.** The Sign In button stays
  `disabled` forever, so nothing can log in — including Playwright. There is no error; the
  JS chunks 404 silently. Fix: kill the frontend, `Remove-Item -Recurse -Force .next`,
  restart. **This happened three times in one session.**
- **`nest start --watch` orphans its children.** Stopping the task kills the wrapper; the
  compiler and `dist/main` keep running and hold port 4000. Two orphaned watchers then race
  and `app.listen()` fails with an EMPTY error object — nothing says "port in use". Find
  them with
  `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*jobfit-backend*' }`
  and kill all of them. Same shape as the AI-service child-process note in the 08-07 handoff.
- **`npx prisma generate` EPERM** needs EVERY jobfit node process dead, not just the dev
  server — the orphans above hold the query engine too.
- **Redis: port 6379 is owned by another project's container (`coorad-redis`).** JobFits is
  currently sharing it. `docker start jobfit-redis` fails with "port is already allocated";
  the sensible move is to use what is there rather than fight for the port. Docker Desktop
  also has to be running at all — it was not, and the backend's only symptom was
  `ECONNREFUSED 6379` buried in a stack trace.
- **PowerShell here-strings mangle git commit messages** containing quotes or `--`. Git
  receives word-split pathspecs and the commit silently fails. **Write the message to a file
  and use `git commit -F <file>`.** Same for `git merge -F`.

## 3. What was built (08-08 → 08-09)

### A. Application status: one road in
`docs/STATUS_LIFECYCLE_PLAN.md` · commits `4e0666e` → `819117c`

Four bugs around the OFFER stage turned out to be one shape: **the lifecycle rules were a
reference book callers were trusted to consult.** Measured: **7 of 9 status-write sites
skipped the transition check, and 6 of 9 wrote no audit row at all** — including accept,
decline, negotiate and rescind, the four moments that decide a hire.

`ApplicationTransitionService` is now the only road to a status write. It takes the **actor**
(`CANDIDATE` / `EMPLOYER` / `SYSTEM`) as a parameter rather than inferring it from which file
the caller stands in — which is exactly why `offer.service.ts` enforced nothing: it held both
paths in one file, so neither entitlement rule felt like it applied.

- `SYSTEM` skips the entitlement check but still obeys `TRANSITIONS`. A test pins that.
- **Compare-and-swap**, not just read-in-transaction: Prisma defaults to READ COMMITTED, so
  two employers dragging the same card could both read `INTERVIEW` and both write. The loser
  now gets a 409.
- **Both** audit tables are written. They were split by actor (`ApplicationStageHistory` for
  the employer, `ApplicationTimeline` for the candidate) and the offer module wrote to
  neither.
- A **guard spec** scans `src/**` for status writes outside the chokepoint and fails the
  suite. Proven by planting a real bypass and watching it fail, then removing it.

**Result: 0 of 10 unguarded, 0 of 10 without an audit row.** The denominator moved because
the guard found a tenth site the audit had missed — `ApplicationRepository.save` wrote status
in its UPDATE branch.

**Verified end to end: 33/33 live checks.** The audit gap in the real database went from
**6 of 8 advanced applications with no stage history to 2** — and the two remaining predate
the change.

### B. Archiving is a view, not a state
Commit `3482542`

A candidate who accepted a job and then tidied their list **disappeared from the employer's
board**, and — because `ARCHIVED` mapped to "Rejected" — was filed under rejections. Archiving
was a shared status, so one party's housekeeping rewrote a record the other party reads, and
it overwrote the outcome underneath it.

Now two per-actor columns (`archivedByCandidateAt` / `archivedByEmployerAt`). `ARCHIVED` is no
longer a transition target; the enum value survives for old rows. Endpoints on both sides.
A spec pins that each repository touches only its own column and never a status.

### C. Offer negotiation is a real conversation
`docs/OFFER_MESSAGES_PLAN.md` · commits `3c613cf`, `bbc78e1`

Reported by the operator: *"I can send only one message and the employer isn't alerted."*
Two bugs, one cause.

- A candidate could send **exactly one** message. The second asked for
  `NEGOTIATING → NEGOTIATING`, which is not a transition, so it threw and was never stored.
- The employer **could not reply at all**, and their only way to write a note
  (`extendOffer`/`updateOffer`) **replaced** the notes column, deleting the candidate's
  message. There was also no GET endpoint for an employer to read an offer.

Cause: a conversation stored in one text column. `OfferMessage` replaces it — rows with
author, timestamp, order and `readAt`. The status transition happens **once**, on the first
message. Unread counts ride on the employer pipeline query, so the board badge shows
"2 new messages" rather than a state that cannot tell a first message from a fifth.

The migration **carried three real user messages across** rather than dropping them.
Migrated timestamps are explicitly not real — none were ever recorded — and the migration
says so.

### E. `/learning` — gaps from the jobs you are actually chasing
`docs/LEARNING_PATH_PLAN.md`, `docs/SKILL_GAPS_V2_PLAN.md` · commits `b7dcf28` → `80aa39b`

The page compared **every user against the same ten hardcoded technology skills**
(`IN_DEMAND_SKILLS`), so a mathematics teacher was told her skill gaps were Docker and
Kubernetes. The list could not vary by user, so **10 of 10 recommendations were irrelevant**
for anyone outside software — a number that needs no experiment.

Gaps now come from the user's own applications, via the already-measured `SkillGapService`
(0.937 groundedness across 44 postings) rather than a second comparison. **Proven with a real
teaching posting: 5 teaching requirements, 0 technology; the software job in the same request
yielded 7 software requirements.** Same code, same user.

**v2, after the operator used it:** grouped by application (a flat list scattered three
unrelated fields together), and **weak matches are no longer hidden**. See §5.3 — this is the
defect this session introduced.

### F. Applied state on job cards
Commit `24efd73`

The job **detail** page has shown "Applied · Screening" since it shipped. Every **list** still
offered "Apply" on a job already applied to, which produced a red error from the unique
constraint. `AppliedPill` now wraps the Apply button in `JobCard` and
`JobRecommendationCard`, so search, saved jobs, dashboard and recommendations all match.

## 4. Product decisions made this session (recorded, not accidental)

| # | Decision | Why |
|---|---|---|
| D1 | `SCREENING → OFFER` allowed | Employers do skip interviews for strong candidates. `SUBMITTED → OFFER` stays forbidden — nothing has evaluated that candidate. |
| D2 | `REJECTED → SCREENING` reopen | Re-extending an offer to someone previously closed out worked before the rules were enforced. **`WITHDRAWN` gets no such door** — walking away is the candidate's decision. |
| D3 | `NEGOTIATING → OFFER` | `updateOffer` always treated `NEGOTIATING` as editable; without this, revised terms mid-negotiation would have started failing. |
| D4 | Declining an offer sets `WITHDRAWN`, not `REJECTED` | `REJECTED` reads as "the employer rejected them" — the opposite of what happened — and was never a status a candidate may assert about themselves. The `Offer` row still records `DECLINED`. |
| D5 | Accepting withdraws other applications (was `ARCHIVED`) | `ARCHIVED` was never reachable from `OFFER`. `WITHDRAWN` is legal and truthful. |
| D6 | No course links on `/learning` | Gaps are full requirement sentences; a search URL built from one returns junk. A bad link dressed as a recommendation is worse than no link. |

## 5. Measurements that said NO (do not re-litigate without new data)

Carried forward from 08-07, all still standing: **LLM `fitScore` is unusable** (ρ 0.137 /
−0.065); **semantic embeddings for skill↔requirement matching failed**; **AI Recruiter
auto-advance threshold is not measurable yet**.

Two more, from this session:

**5.1 — Skill normalisation was refused, using §5.2 of the previous handoff.** The obvious
next step on `/learning` is merging "curriculum planning" with "curriculum development".
That needs semantic similarity, which was already measured and rejected: the software
candidate outscored the mechatronics candidate on an automotive job (0.629 vs 0.482), and
*"Automotive Eng Tech" ↔ "Automotive Industry"* (0.467) ranked **below** *"Teamwork" ↔
"collaborate as a team"*. Both spellings now simply appear. **Do not re-open this.**

**5.2 — The `/learning` matcher was NOT changed.** `management` counting as a signal word is
deliberate; `themeWordsOf` exists because removing domain words broke the welding case. The
defect below was in reporting, one layer up.

**5.3 — A defect this session introduced, then fixed.** Measured on the operator's real CV
against three real postings: 19 requirements, 11 reported as gaps, **7 counted as covered —
and one of those was false.** The CV says *"Effective Time Management"*; the matcher strips
`effective` as generic and matches on `management`, which also appears in *"Classroom
behaviour management"*. The page told a software engineer he has classroom behaviour
management.

The matcher had labelled that `PARTIAL` and its own comment says *"the UI must not present it
as if the CV said the whole thing"*. `getSkillGaps` read `result.missing`, which collapses
EXACT and PARTIAL into one bucket — **the distinction the service was explicit about was
discarded one layer up.** Gaps now carry `coverage: MISSING | PARTIAL` and a partial one names
the skill that caused it, so the reader can overrule it.

## 6. Open issues, roughly by value

**1. Résumé extraction produces generic single-word skills.** The operator's CV parses to
*Programming, Communication, Technical Skills, Hardware + Software*. Those match broad text
and evidence almost nothing, which makes every gap list **shorter than the truth** — two of
three "covered" items on the measured CV were weak matches. This is the biggest remaining
correctness problem on `/learning`, and it lives in résumé parsing, not the learning page.

**2. No notification when an offer message arrives.** The employer sees the unread badge only
if they happen to open the board. The notification module exists but
`ApplicationStatusChangedListener` is still a `TODO` stub.

**3. Stale offers on closed applications.** `soviseth869@gmail.com` has four offers reading
`EXTENDED`/`NEGOTIATING` on applications that are `ACCEPTED` or `ARCHIVED`. This already
caused one live bug (commit `51636a1`: accepting an offer failed with
`Invalid status transition: ACCEPTED → WITHDRAWN`, because the auto-withdraw sweep tried to
close them). The sweep now filters to applications it can legally close, but **the rows are
still there and still show in the candidate's "Active Offers" list.** Two options: close them,
or have that list filter on the *application's* status. The second fixes the class.

**4. `useOffers` is the only hook that fetches outside React Query.** It caused a crash screen
on a lapsed session (fixed in `54aa653` by adding the missing `.catch`). Converting it would
get retries, caching and error handling for free and remove the one place this class of bug
can appear.

**5. ESLint is not set up at all** — no config, not a dependency. Phase 4 of the lifecycle
plan shipped the guard as a jest spec instead, deliberately. Adopting ESLint is a real
decision, not a side effect.

**6. `job.mappers.ts` still defaults `type: "Full-time"`, `level: "Mid-level"`,
`industry: "Technology"`** on every job. Job cards render the first two as pills, so every card
still claims "Full-time · Mid-level" regardless of the posting. **Carried over from 08-07 and
still not fixed.**

**7. Phase D (GPU) still hardware-blocked.** See `docs/RAG_PHASE_D_HANDOFF.md`.
