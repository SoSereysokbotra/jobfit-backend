### What that fix was

`_prisma_migrations` recorded `20260825120000_match_report_payload_version` as applied, but
**no file existed anywhere** — not on any of 30+ local/remote refs, not in a stash, not on
disk, only one clone.

**Smoking gun:** that row has `applied_steps_count = 0`; every other migration has `1`.
Prisma ran no SQL for it — it was marked applied via `migrate resolve --applied`, and the
column was created another way (manual `ALTER` or `db push`).

Reconstructed read-only from `information_schema`:

```sql
ALTER TABLE "match_reports" ADD COLUMN "payloadVersion" INTEGER NOT NULL DEFAULT 1;
```

Exact byte-for-byte recovery was attempted and **failed**: Prisma's checksum is
`sha256(migration.sql with LF endings)` — verified against a migration we do have — and
none of 7 candidate formats matched the recorded `fb96ae5f…`. The original carried prose
comments that cannot be guessed.

`payloadVersion` was also added to `schema.prisma`. **This half matters more than the
file:** without it the schema lacks a column the migrations create, and the next
`migrate dev` would propose **DROPPING** it.

### Verified after

- `prisma migrate status` → **"Database schema is up to date!"** (33 migrations)
- `prisma migrate deploy` → exit 0, *"No pending migrations"*, **no checksum error**
- DB untouched: checksum `fb96ae5f…` unchanged, `finished_at` unchanged, 26 rows intact

### ⚠️ Gap worth knowing

`migrate deploy` accepted a migration whose checksum does **not** match the recorded one,
silently. A genuinely modified applied migration would also pass CI. Not a problem today;
worth knowing it is not a safety net.

### Unverified

Nothing in this repo reads or writes `payloadVersion`. Data says it is real (25 rows at
v1, **1 at v2**, all 12–25 Aug; both versions have identical top-level payload keys, so v2
changed something nested or semantic). **The purpose is inferred, not confirmed** — the
code that writes v2 is on no branch here. The migration header and schema comment both say
so; do not upgrade that to a claim.

### The two headline findings

**(a) The AI service's `/health` lies.** It returns `{"status":"ok"}` with Ollama dead —
liveness for the FastAPI process, not readiness for the models. **Never derive AI status
from it.** `AiAvailabilityService` derives state from *real call outcomes* first and only
probes `/ready` when nothing recent answers. There is a test pinning that a real failure
overrides a "ready" probe.

**(b) The 60 s generate timeout was below the measured cost of the service's own core
task.** Résumé parse takes **73.5 s** on a short CV on this hardware. Every upload failed —
and it had nothing to do with availability. Raised to 240 s (AI service) / 250 s (backend).
The backend value **must exceed** the AI service value, or the backend gives up first and
the structured `MODEL_TIMEOUT` never surfaces.

## 5. NEXT: testing the degradation work

This is where the session stopped. **1031 unit tests mock the AI client** — they prove the
logic, not the wiring. Only one scenario has been verified against a real outage:
`/health/ready` with the AI down correctly returned `degraded: true`, `reason: NETWORK`,
HTTP 200 in 0.59 s.

Five scenarios, all stageable locally by stopping things:

1. **AI service down** (stop uvicorn) — parse → `FAILED`; `embeddingStatus` → `FAILED`
   with a reason; `/recommendations/readiness` → `EMBEDDING_FAILED` not "no matches";
   cover letter → `generatedBy: 'template'`, logged at **error**
2. **AI up, Ollama down** — the case `/health` lies about. `/ready` → 503
   `OLLAMA_UNREACHABLE`
3. **Model missing** (`ollama rm qwen3:4b`) — `/ready` → 503 `MODEL_NOT_INSTALLED`,
   `missing: ["qwen3:4b"]`. **~30 seconds, needs only Ollama — start here**
4. **New user, AI down** (§7) — empty list, but readiness explains why
5. **Recovery** — should partly *fail*: a `FAILED` embed only retries when the profile
   changes. Confirming that limitation is as valuable as the happy path.

Scenarios 2–3 are already covered by `pytest` in the AI service. 1, 4, 5 are
integration-level: do them **manually once**, automate only if they break twice.
