## 2. What was built

### A. Cambodian job ingestion — bongthom.com + jobnet.com.kh
`docs/INGESTION_KH_PLAN.md` · backend `f78000d` (on `main`)

The corpus was 61 jobs, 43 of them US postings from TheMuse, for a product whose users are
in Cambodia. Now **367 jobs, 305 of them Cambodian.**

| source | jobs | `employmentType` | `location` | avg description |
|---|---|---|---|---|
| internal | 19 | 0 | 19 | 84 |
| **BONGTHOM** | **276** | 0 | 0 | **45** |
| **JOBNET** | **29** | **29** | **29** | **2,099** |
| THEMUSE | 43 | 0 | 43 | 4,562 |

**bongthom is FEED-ONLY, deliberately.** It advertises an RSS feed of 275 postings, but
its detail pages wrap the description in `<span class="noselect">` with
`.noselect { user-select: none }` — an anti-copy measure — **and its RSS omits the
description entirely**. Both say: syndicate the listing, not the body. So we take title,
employer, id and link, and nothing else. The 45-character "descriptions" are titles. This
cost was accepted knowingly.

**jobnet is read in full**, because it is the opposite case: zero anti-copy measures, and
the entire description published as schema.org `JobPosting` JSON-LD, which exists to be
machine-read. Two quirks of their implementation are handled and pinned by tests: keys are
**capitalised** (`Title`, not `title`), and the block contains **unescaped control
characters** so a plain `JSON.parse` throws.

⚠️ **Neither site's Terms of Use has been read** — both are JS-rendered, so a fetch returns
an empty shell. `robots.txt` is absent on both, which declares nothing either way. Someone
must open both in a browser. Mitigations already in place: `sourceType: EXTERNAL` (the
server refuses in-app applications and sends users to the source, so traffic flows *to*
them), an identifying User-Agent, and per-host rate limiting.

Run it:
```bash
npx ts-node -r tsconfig-paths/register scripts/ingest.ts BONGTHOM 300
npx ts-node -r tsconfig-paths/register scripts/ingest.ts JOBNET 30
```
**Read the skip count.** >20% skipped means the parsing assumptions broke; the fix is to
look at what came back, not to loosen the parser.

### B. Job Tracker — backend
`docs/JOB_TRACKER_PLAN.md` · backend `cbcb455`

A drag-and-drop board (SAVED / APPLIED / INTERVIEW / OFFER / REJECTED) for jobs applied to
on other sites.

**It does NOT reuse `Application`, and that decision is the whole design.** An Application
records what an *employer* decided, and `ApplicationTransitionService` **refuses** a
candidate asserting INTERVIEW/OFFER/REJECTED. A board is the opposite: the user drags their
own card, meaning "this is where I think I am". Wiring it to `Application.status` would
either refuse every drag or let a candidate write into an employer's pipeline — the mistake
`ARCHIVED` was before it became a per-actor column. Also, these jobs *cannot* have an
Application: the server refuses in-app applications to EXTERNAL postings.

So: `tracked_jobs`, its own `TrackedJobStage` enum, and **any stage may follow any other,
including backwards** — moving a card back is a correction to one's own notes.

- **The snapshot is the point.** `title`/`companyName`/`url` are copied onto the card, not
  read through `jobId`, so it survives the posting being taken down (bongthom 404'd 9 of 43
  during ingestion), never being in our DB, or being re-ingested. `jobId` is
  `ON DELETE SET NULL`.
- A move **renumbers the affected columns in one transaction**. Half a move leaves a card
  in two columns or none.
- An out-of-range `position` is **clamped, not rejected** — a stale client index must not
  fail a drag the user already saw land.
- `appliedAt` is stamped the **first** time a card reaches APPLIED, never overwritten.

8 endpoints under `/api/v1/tracker`. 26 specs.

### C. Job Tracker — frontend (UNCOMMITTED)

`/tracker`, plus a **Job Tracker** sidebar tab under *YOUR JOURNEY*.

- **Native HTML5 drag-and-drop, no library.** The alternatives are unmaintained
  (`react-beautiful-dnd`) or much larger than the feature (`@dnd-kit`). **The cost: HTML5
  drag events do not fire on touch**, so dragging is pointer-only — which is why every card
  also opens an editor with a stage dropdown.
- **The drag is optimistic**, using the same insert-and-renumber logic the server uses, so
  the card does not shuffle when the response lands. On failure the exact previous board is
  restored rather than refetched (a refetch races the next drag).
- Columns `flex-1 min-w-[17rem]` so they fill a wide screen and only scroll horizontally
  when the viewport cannot give each its minimum.

### D. Clicking "Apply Externally" now adds a tracker card

Previously a plain `<a target="_blank">` with no handler, and its caption claimed
*"Applications made there can't be tracked in JobFits"* — true when written, false once the
tracker existed. Now it also posts the job to the tracker under **Applied**, and says so
with a link. A 409 (already tracked) is treated as success. The link stays a real `<a>` so
no popup blocker can swallow it. Logic lives in one hook, `useExternalApply`, because the
three apply surfaces drifted apart once before.

## 5. Measurements that said NO (do not re-litigate without new data)

Carried forward and still standing: **LLM `fitScore` is unusable** (ρ 0.137 / −0.065 vs 150
hand-graded pairs, BAD scoring above GREAT); **semantic embeddings for skill↔requirement
matching failed**; **skill normalisation refused**; **the `/learning` matcher must not
change**.

**5.1 — The BM25 leg of hybrid retrieval is dead, and the obvious fix is worse.**
`websearch_to_tsquery` ANDs unquoted terms, and the candidate query is headline + every
résumé skill + every past job title, so one posting must contain all of them. Every user
with a parsed résumé gets **0** sparse hits (OR-ing gives 26–52). But a clean A/B on
identical data:

| BM25 query | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|
| AND (ships) | **0.500** | 0.500 | **0.606** |
| OR (candidate fix) | 0.458 | 0.500 | 0.563 |

On a small corpus an OR of 20+ terms matches most of it, so the sparse list stops
discriminating and RRF blends noise into a dense ranking that was working. **Reverted.**

**5.2 — The prompt is the wrong layer for splitting résumé skills.** `resume_parse_v5`
states "one skill per entry" with worked examples and still glues them half the time
(v4: 6/8 runs bad, v5: 4/8, n=8 — inside the noise). Splitting moved into code
(`splitSkillEntry`). **The default stays `v4`**: best-measured, not newest.

## 6. ⚠️ The eval harness can no longer judge matching work

This is the single most important thing to fix before touching retrieval or scoring again.

- **Half the labels were lost.** `snowrin168@gmail.com`'s user row was deleted and the email
  re-registered; `match_labels` cascades on user delete. **100 pairs / 2 candidates → 50
  pairs / 1 candidate.** No `USER_ACCOUNT_DELETED` audit row, so it did not go through the
  admin path.
- **The one remaining candidate has no résumé**, so `experience` is a **constant 40** across
  every labelled pair — 25% of the match weight, correlating with nothing, and unimprovable
  because no experience scorer can move a number for a candidate with no experience data.
- **Not one labelled job is from bongthom or jobnet.** The corpus went 62 → 367, so the 12
  relevant jobs now compete with ~305 candidates the harness has no opinion about. Retrieval
  duly fell (Recall@10 0.500 → 0.333, nDCG 0.606 → 0.425). **That is not a regression** and
  must not be tuned against.

**The real check was done instead, by asking what a user gets:** `strong@seed` (Senior
Full-Stack) now has **four real Cambodian software jobs in their top 10** where there were
none. And the dilution worry did not materialise — bongthom is 75% of the corpus and appears
**zero times** in either checked user's top 10, because thin title-only text produces a weak
embedding and correctly ranks low.

**Unblock: re-label, including candidates WITH résumés and Cambodian jobs.**
`eval-export-worksheet.ts` → label → `eval-load-labels.ts`.

Two harnesses exist:
- `scripts/eval-retrieval.ts` — which jobs come back (Recall/MRR/nDCG).
- `scripts/eval-score-calibration.ts` — **new**; Spearman ρ of the match score *and each
  sub-score* against the human labels. Nothing measured the sub-scores before it, because
  the breakdown is computed after retrieval and no retrieval metric moves when it changes.

Last calibration (n=1 candidate, 50 pairs — weak):
```
TOTAL 0.669 · salary 0.684 · skills 0.573 · location 0.455 · other 0.518 · experience 0.000
```
`other` (industry) was **−0.667** until a bug was fixed: `companies.industry` stores a UUID
while `Profile.desiredIndustries` stores names, so the match branch was unreachable and the
*worse* score landed on jobs that had industry data — which are the good ones.

### §7.4 — `formatSalaryRange` is worse than "$0K – $0K"

```ts
export function formatSalaryRange(job) { return `$${job.salaryMin}K – $${job.salaryMax}K`; }
```

The currency (`$`) and the unit (`K`) are both hardcoded. On a corpus that is now 83%
Cambodian, a job paying **500** renders as **`$500K`** — wrong by three orders of magnitude,
and it *looks like data* in a way `$0K` does not. `Profile` has `salaryCurrency`; `Job` has
no currency or period column at all, and the corpus already mixes monthly (KH boards) with
annual (TheMuse). Fixing only the null case leaves the bigger lie in place.

### §6 — the eval-label loss has a mechanical cause, and it will recur

`snowrin168@gmail.com` could not have been lost through the app's delete path:
`UserRepository.delete` is a **soft** delete and `User.email` is `@unique`, so the address
would still have been occupied and re-registration would have failed. The row was
hard-deleted out of band — which is the workaround forced by two real defects:

1. `LoginHandler` never checks `deletedAt`, so a soft-deleted user can still log in (the
   soft delete does nothing user-visible).
2. The retained unique email means a deleted user can never re-register.

Until both are fixed, out-of-band hard deletes stay the only way to actually remove someone
— and `MatchLabel` is `onDelete: Cascade` on the user, so the ground-truth set is one manual
`DELETE` away from vanishing again. Consider `SetNull` on `MatchLabel.userId`, or exporting
the label set to a file no `DELETE` reaches.

### New items not in §7, ordered by damage

1. **No email is ever sent** (`MailerService` is a `console.log` stub) while login refuses
   unverified accounts — **no new user can sign in on the deployed instance.** Recorded in
   the scorecard as a *notification* gap; it is an *authentication* outage.
2. **`PATCH /users/:id/subscription` and `DELETE /users/:id` have no role or ownership
   check.** Any authenticated user can grant themselves PROFESSIONAL, or delete any account
   — with no audit row, which is exactly the shape of the §6 incident.
3. **`recommendations` is never invalidated.** The re-embed listener fires; nothing deletes
   the cached rows and there is no scheduler. §8 records this as an operator hazard around
   deploys; it is also a user-facing bug — changing your CV never moves your matches.
4. **`GET /recommendations/scout` cannot return a job created after the user's first
   recompute**, because it reads the same cache. The 305 Cambodian jobs are invisible to
   every scout user.
5. **No rate limit on any AI route.** `@RateLimit` is opt-in and only auth routes use it.
