## 3. What was built (08-09 → 08-10)

Every item is one entry from §6 of the previous handoff. All six workable ones are done;
the seventh is confirmed blocked.

### A. An offer is only as live as the application behind it — §6.3
Backend `cb31eac` · frontend `3dac173`

The handoff asked for one thing (filter the Active Offers list) and the code turned out to
have the same hole in four places. **Four call sites decided "can this be acted on?" from
the offer's own status alone.** One had been patched (`51636a1`); accept, decline and
post-a-message had not, so each waved a stranded offer through and failed deep inside the
transition service with `Invalid status transition: ACCEPTED → WITHDRAWN` — a message
about the mechanism, not the reason.

`ACCEPTABLE_FROM` states the rule once, derived from `TRANSITIONS` exactly as
`WITHDRAWABLE_FROM` is, so it cannot drift. The response reports `lapsed` rather than
dropping the row: the candidate **did** receive that offer, and filtering it out would
rewrite their history to tidy up a display problem. The card grows a third past state —
a lapsed offer was never accepted *or* declined.

⚠️ **Pinned by 9 unit specs, NOT seen working on real data** — the rows it was written for
no longer exist (§2). To watch it work, strand an offer deliberately.

### B. Notifications — §6.2, and the sharpest lesson of the session
Backend `e404aa0` · frontend `6132755` · bell mounted in `3023563`

The module was three empty `@OnEvent` stubs and a service whose two methods had empty
bodies, with no table behind them. Two things the handoff did not know:

1. **`ApplicationStatusChangedEvent` is published from exactly one place** —
   `ApplicationService.updateStatus`, the candidate changing their *own* application,
   which is the single case needing no notification. Every employer-driven move reached
   the chokepoint from a different caller and published nothing. The stub listener would
   not have fired for any status change worth notifying about even with a body written.
2. **An `@OnEvent` listener could not be correct here regardless.** `emitAsync` fires while
   the transaction is still open, so a listener can notify someone of a hiring decision
   that then rolls back.

So **the chokepoint writes the notification itself, on the caller's transaction**, beside
the two audit rows it already writes. Recipient is the counterparty, never the actor —
which follows from `actor`, the parameter the chokepoint already demands rather than
infers. Offer messages are not status transitions after the first, so `OfferService`
notifies for those itself; that is the reported bug.

**Then ESLint found that `NotificationBell` was imported in `topnav.tsx` and never
rendered.** The bell, the badge, the feed page and the hooks all existed and were complete.
The whole feature — including everything built above — was unreachable from the app. Nobody
found that by using the page.

**Verified end to end.** Moving `soviseth869@gmail.com`'s *Primary School Mathematics
Teacher* application `SCREENING → INTERVIEW` as the employer produced exactly one
notification, addressed to the **candidate** (the counterparty, not the actor who moved
it), unread, with a resolving deep link. The table held 0 rows before and 1 after, so
nothing else wrote it. Looking at that row also caught a grammatical slip in the fallback
body (`"… — now interview."`) that no test would have failed on — the third defect this
session found by reading output rather than code.

## 4. Product decisions made this session

| # | Decision | Why |
|---|---|---|
| E1 | A lapsed offer is reported, not filtered out | The candidate did receive it. Deleting it from the response rewrites their history to fix a display problem. |
| E2 | Notifications are written transactionally by the chokepoint, not by an event listener | `emitAsync` fires inside the open transaction, so a listener can announce a decision that rolls back. |
| E3 | The stub `ApplicationStatusChangedListener` is deleted, not filled in | It could not be made correct; leaving a stub beside the real mechanism is worse than removing it. |
| E4 | Existing job rows are NOT backfilled with a type or level | A fabricated value in the database is indistinguishable from an employer's own answer. |
| E5 | `splitSkillEntry` does not split on `and` | "Health and Safety" is one skill and nothing distinguishes it from "Docker and Kubernetes". Under-crediting is the safe direction. |
| E6 | `resume_parse_v5` is NOT the default | Best-**measured**, not newest. See §5.1. |
| E7 | ESLint warnings are left visible, not silenced | A count that is always zero cannot be a signal. |

## 5. Measurements that said NO (do not re-litigate without new data)

Everything from 08-07 and 08-09 still stands: **LLM `fitScore` unusable** (ρ 0.137 /
−0.065); **semantic embeddings for skill↔requirement matching failed**; **skill
normalisation refused**; **the `/learning` matcher must not change**; **AI Recruiter
auto-advance threshold not measurable yet**.

One more, and it is the interesting one:

**5.1 — The prompt is the wrong layer for skill splitting.** `resume_parse_v5.txt` adds
explicit rules with worked examples: no section headings, no bare categories, **one skill
per entry, split every line**. Measured n=8 runs each against `qwen3:0.6b` on a synthetic
CV with a labelled skills section:

| | unusable skill entries | runs with at least one |
|---|---|---|
| `v4` | 14 of 43 | 6 of 8 |
| `v5` | 12 of 45 | 4 of 8 |

**A real improvement, and inside the noise at n=8.** The run output also showed the
*dominant* defect was not the category labels the handoff described — v4 produced those in
only 1 of 8 runs. It was this:

```
'Languages: C++, Python, TypeScript'   ← returned as ONE skill
```

Three real skills glued into a string no employer writes and the matcher cannot see inside.
**v5 states the rule as plainly as it can be stated and still glues them together half the
time.** So splitting moved into code (`splitSkillEntry`), applied at **read** time as well
as write time so the parses already in the database are repaired. The v5 rules stay — they
cost nothing and should help a larger model — but nothing depends on them, and **the
default stays `v4`**.

Caveat that matters: this measures only the splitting defect, on a synthetic CV. The
operator's real CV is not in the repo, so v5 is still unmeasured on the 7-field accuracy
axis that chose v4.
